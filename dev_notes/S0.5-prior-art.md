# S0.5 -- prior art sweep

Run 2026-07-27 against CRAN (24,424 packages in `tools::CRAN_package_db()`), the
Numerical Mathematics task view, and the r-universe function index.
Scripts: `dev_notes/spikes/S0.4_S0.5_fetch.R`, `S0.5_funcsearch.R`, `S0.5_deepcheck.R`.

## Conclusions

1. **MINRES, LSQR and LSMR are absent from CRAN as Krylov solvers.** Confirmed three ways.
2. **Nothing on CRAN offers a function-space or operator-discretisation abstraction.**
   Confirmed; the Hilbert layer has no R prior art to be compatible with.
3. Two packages the plan does not mention need to be added to the landscape:
   **`sanic`** (CRAN, Krylov linear solvers in C++) and **`amatrix`**
   (GitHub/r-universe, by the eigencore author, backend-agnostic matrix classes).
4. eigencore overlaps linop's Layer 1 much more than the plan assumes. Separate write-up:
   `dev_notes/eigencore-audit.md`.

## 1. MINRES, LSQR, LSMR

Three independent checks.

**Title/Description across all 24,424 CRAN packages.** `MINRES`: 0 hits. `LSMR`: 0 hits.
`LSQR`: 1 hit (`lazymatrix`, "Perform Complex Matrix Operations Symbolically on Sparse
Matrices").

**Exported function names**, from downloaded `NAMESPACE` files:

| Package | CRAN | Krylov-token exports |
|---|---|---|
| `pracma` 2.4.6 | yes | none exported matching the tokens |
| `sanic` 0.0.2 | yes | `lanczos`, `arnoldi` |
| `gmresls` 0.2.3 | yes | `gmresls` |
| `pcg` 1.1 | yes | none |
| `lazymatrix` 0.1.0 | yes | `lsqr` |
| `TSSS` 1.3.4-7 | yes | `lsqr` |
| `diffcp` 0.1.1 | yes | none |
| `optR` 1.2.5 | yes | none |
| `SparseM` 1.84-2 | yes | none |
| `svd` 0.5.8, `rARPACK` 0.11-0 | yes | none |
| `withinr` | **not on CRAN** | (LSMR hit was r-universe only) |

**The two `lsqr` exports are not the Paige-Saunders solver.** `TSSS` is time-series state
space modelling; `lazymatrix` is symbolic sparse matrix manipulation. Neither offers LSQR
as a matrix-free least-squares solver. The single r-universe `lsmr` hit, `withinr`, is a
fixed-effects econometrics package and is not on CRAN.

**Task view.** The Numerical Mathematics view lists `Matrix`, `MASS`, `expm`, `QZ`,
`geigen`, `SparseM`, `rmumps`, `sanic`, `Rlinsolve`, `optR`, `svd`, `irlba`, `rARPACK`,
`RSpectra`, and others. Asked directly, it does not mention matrix-free operators, MINRES,
LSQR, LSMR, or function-space/operator discretisation.

**Caveat on the r-universe API.** Single distinctive tokens (`minres`, `lsqr`, `lsmr`,
`gmres`, `bicgstab`) return usable results. Multi-word queries do not: "conjugate gradient"
returned 751 packages and "matrix-free" returned 6,605, which is OR-matching across all
fields, not phrase search. Only the single-token results above are relied on.

**One caveat that cannot be closed cheaply.** A package could implement MINRES internally
without exporting a matching name or advertising it. The claim that is safe to make in
public is the one this sweep supports: *no CRAN package exposes MINRES, LSQR or LSMR as a
user-callable solver*. Do not write "no R implementation exists".

**Also confirmed:** `psych` and `EFA.dimensions` match "minres", but as *minimum residual
factor analysis*, an unrelated estimator. Worth remembering, because a naive future search
will surface them again.

## 2. `sanic` -- a comparator the plan misses

`sanic` 0.0.2, "Solving Ax = b Nimbly in C++", is in the task view under core linear
algebra and exports `lanczos` and `arnoldi`; its Description mentions BiCGSTAB and Krylov
methods. It is a direct comparator on the linear-solve side alongside `Rlinsolve`, and
section 11's comparator list should include it.

Not investigated further: whether it accepts an operator or requires an assembled matrix.
Do that before any benchmark table is published. Given the plan's section 15 rules, it also
belongs in the "state of the field" of any paper.

Other linear-solve packages found: `gmresls` (GMRES(k) least squares -- note this is
adjacent to LSQR/LSMR territory), `pcg` (preconditioned CG), `optR` (Gauss/LU/CGM/Cholesky),
`rmumps` (MUMPS direct sparse), `SparseM`.

## 3. `amatrix` -- the eigencore author is building an adjacent abstraction

`bbuchsbaum/amatrix`, GitHub, created 2026-04-12, last pushed **2026-07-24**, three days
before the plan was drafted. Not on CRAN; served from `bbuchsbaum.r-universe.dev`. 17,745
lines of R, 159 exports, zero stars, MIT.

> "Backend-Agnostic Matrix Extensions. Matrix-compatible S4 classes with backend-dispatch
> hooks for accelerated execution and predictable CPU fallback."

`Suggests: amatrix.mlx, amatrix.arrayfire, amatrix.opencl, amatrix.metal` -- GPU backends
as separate packages, with `Additional_repositories` pointing at the author's r-universe.

### It is not matrix-free, and that is the whole distinction

Read in full: `R/classes.R` (207 lines), `R/generics.R` (102 lines).

`adgeMatrix` **contains** `Matrix::dgeMatrix` (classes.R:86-89) and `adgCMatrix` contains
`Matrix::dgCMatrix` (classes.R:100-103). They inherit the `@x` data slot: these are stored
matrices. The virtual base `aMatrix` (classes.R:53-73) adds `preferred_backend`, `policy`,
`precision`, `object_id`, `src_id`, `finalizer_env` -- metadata about *which device holds
the data and which backend computes*, not about an operator's action.

The one lazy class, `aTransposeView` (classes.R:144-152), is "a zero-copy structural view"
that holds a reference to a stored `adgeMatrix`.

A repository-wide search for `matrix.free|matrix_free|matvec|LinearOperator|apply_fun`
finds only `.kron_matvec` (`R/kronmatrix.R:167-245`), which multiplies by a Kronecker
product of two *stored* factors, and comments in `R/irlba.R:5,87` about keeping a matrix
"resident on device". No constructor takes an apply function.

So: **amatrix is about where a matrix lives; linop is about matrices that never exist.**
They are complementary. An `adgeMatrix` is a natural `linop` leaf via `linop.adgeMatrix()`,
which would put linop's solvers on GPU-resident data without either package changing.

### What linop should take from it

`backend-registry.R` (29 KB), `backend-planning.R` (19.9 KB) and `backend-explain.R`
(7.9 KB), with exports `amatrix_backend_plan`, `amatrix_backend_capabilities`,
`amatrix_backend_status`, `amatrix_backend_health_probe`, are a working implementation of
the same problem plan section 3 sets out for the backend protocol and `plan_eigs()`. Read
them before designing that protocol rather than after. **Not read in this spike.**

## 4. Hilbert side: still empty

Searches for `linear operator`, `operator discretisation`, `Hilbert space`, `Chebfun`,
`ApproxFun` returned nothing relevant. The `Hilbert space` hits are all reproducing-kernel
statistics (`ktweedie`, `KPC`, `fdadensity`, `bigPLSR`, `multiCCA`, ...), which use RKHS as
a modelling device, not as an operator-theoretic setting.

The task view's function-approximation section lists only `minimaxApprox` (Remez algorithm)
and the orthogonal-polynomial packages `orthopolynom`, `PolynomF`, `polynom`. There is no
Chebfun/ApproxFun equivalent.

Plan section 2's provisional claim, "No Chebfun or ApproxFun equivalent on CRAN --
provisional pending a Numerical Mathematics task view read", is now **confirmed**, and the
"provisional" qualifier can be dropped.
