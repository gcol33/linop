# S0.3 -- vendored PRIMME build

Run 2026-07-27. PRIMME 3.2 (`include/primme.h:41-42`), cloned from
github.com/primme/primme, BSD 3-clause (`COPYING.txt`, College of William & Mary).
Scripts and artefacts: `dev_notes/spikes/S0.3_*`.

## Verdict

Vendoring works, on Windows and macOS arm64. One blocker was found, diagnosed and solved,
and it is not the one plan section 13.3 anticipated.

| Platform | Build | Link against R's BLAS/LAPACK |
|---|---|---|
| Windows x86_64, Rtools45, gcc 14.3.0 | **yes**, 9.8 s | **only with a 2-routine shim** |
| macOS arm64 (Darwin 25.5.0), clang | **yes** | **yes**, unaided |
| Linux | not tested | not tested |

## 1. The library builds

```
make lib CC=gcc CFLAGS="-O2 -pipe -DNDEBUG -DF77UNDERSCORE" -j8
```

produces `lib/libprimme.a`, 4.9 MB, 888 defined text symbols, in 9.8 s on the i9-14900K.
With `-DPRIMME_WITHOUT_FLOAT` it is 1.9 MB. macOS arm64 with `CC=clang` gives 1.9 MB.

### Two Windows build obstacles, both incidental

**`TMPDIR` inherited as `C:\WINDOWS`.** Every compile died with
`Cannot create temporary file in C:\WINDOWS\: Permission denied`, make error 127. gcc
works standalone; the cause is that MSYS `sh`, which make spawns per recipe, clears `TMP`,
so gcc falls back to `C:\WINDOWS`. **Fix: add `-pipe` to `CFLAGS`**, which keeps the
assembler stage in a pipe and needs no temp file at all. This is a one-flag fix and should
go straight into the vendored `Makevars` rather than being rediscovered.

Note for whoever debugs this next: a trivial `gcc -c` test does *not* reproduce it if the
test file fails to compile, because the failure is in the assembler stage. Use a file that
actually compiles.

**PRIMME's own build system is fine.** `Make_flags` lists MinGW as a supported POSIX
system and no patching of the makefiles was needed.

## 2. The real blocker: R does not ship the LAPACK routines PRIMME needs

`libprimme.a` has 70 undefined BLAS/LAPACK symbols. Comparing against the export tables of
`Rblas.dll` (79 exports) and `Rlapack.dll` (627 exports) on R 4.6.0:

**37 of the 70 are missing from R.**

- 35 are single precision, `s*` and `c*`. R ships **no** single-precision BLAS or LAPACK at
  all: `dgemm_`/`zgemm_` present, `sgemm_`/`cgemm_` absent. Building with
  `-DPRIMME_WITHOUT_FLOAT` removes all 35.
- **2 are double precision and remain: `zheevx_` and `zhegvx_`**, the expert-driver complex
  Hermitian standard and generalized eigensolvers.

This is not a symbol-table inference. The link fails:

```
ld.exe: libprimme.a(blaslapack.o): undefined reference to `zheevx_'
ld.exe: libprimme.a(blaslapack.o): undefined reference to `zhegvx_'
```

**And it blocks the real-double build too.** `blaslapack.o` is one archive member that
references the complex paths unconditionally, so *any* program linking `libprimme.a` needs
these two symbols, even one that only ever calls `dprimme`. "Just don't use complex" is not
available.

### The blocker is Windows-specific, and the reason matters

On macOS the same two symbols resolve, but **not from R**:

| link line | result |
|---|---|
| `-lRlapack -framework Accelerate` | OK |
| `-framework Accelerate` alone | OK |
| `-lRlapack` alone | **fails on `zhegvx_`** |

So macOS works because Homebrew R uses Accelerate as its BLAS/LAPACK and Accelerate is a
full LAPACK. Windows R uses its own bundled reference subset, which is not. Any platform
where R falls back to its bundled LAPACK will hit this; a Linux build against a distro
OpenBLAS/LAPACK will not.

Plan section 13.3 says "Windows source install of a vendored C library is the main adoption
risk for the backend". Correct, and now specific: **the risk is the LAPACK subset, not the
compiler.** The compile is the easy part.

## 3. The fix, proven end to end

R exports the ingredients even though it lacks the drivers:

| needed | in R? |
|---|---|
| `zheevx_`, `zhegvx_` | **no** |
| `zheev_`, `zheevd_` | yes |
| `zpotrf_`, `ztrsm_` | yes |
| `zhetrd_`, `zungtr_`, `zsteqr_`, `dsterf_`, `dstebz_` | yes |
| `zheevr_`, `zhegv_`, `zhegvd_`, `zstein_` | no |

`zheevx_` can therefore be supplied on top of `zheevd_`: compute the whole spectrum of the
projected matrix and select the requested range. `zhegvx_` reduces to it by Cholesky
(`zpotrf_`) plus two triangular solves (`ztrsm_`), with a back-transform of the
eigenvectors.

This is cheap where PRIMME uses it. Both routines are called only on the **small dense
projected eigenproblem**, whose order is the Krylov basis size, not `n`. Computing all
eigenpairs of a matrix of order ~100 instead of a subset is not a meaningful cost.

`dev_notes/spikes/S0.3_lapack_shim.c` implements both in ~120 lines of C. With it:

```
LINK OK
dprimme OK, 4 smallest eigenvalues of tridiag(-1,2,-1), n=200
  lambda[0] = 0.000244286119   exact = 0.000244286119   |diff| = 1.006e-16   rnorm = 2.075e-10
  lambda[1] = 0.000977084799   exact = 0.000977084799   |diff| = 4.770e-18   rnorm = 1.730e-10
  lambda[2] = 0.002198217029   exact = 0.002198217029   |diff| = 4.705e-16   rnorm = 2.166e-10
  lambda[3] = 0.003907384502   exact = 0.003907384502   |diff| = 5.282e-16   rnorm = 3.162e-10
matvecs: 787
```

Ground truth is the plan's own section 10 closed form, `4 sin^2(k pi / (2(n+1)))`. Agreement
to `5e-16`, through the vendored engine, linked against R's own LAPACK, on Windows.

### Caveats on the shim, before it becomes shipped code

The spike shim is a proof of concept and is **not** ready to vendor:

- `RANGE = 'V'` selection assumes the eigenvalues `zheevd_` returns are ascending, which
  LAPACK guarantees, but the half-open convention `(vl, vu]` was not tested against
  reference `zheevx_`.
- Only `itype = 1` of `zhegvx_` is implemented. PRIMME's usage was not audited to confirm
  that is the only type it requests. **Check before shipping.**
- `abstol`, `lwork` query semantics and `ifail` are stubbed.
- Not tested against complex problems at all. Only the real-double path was exercised
  end to end, because the shim only had to make the link succeed for that test.

The alternative is to vendor `zheevx_`, `zhegvx_` and their missing dependency `zstein_`
from netlib reference LAPACK. That is more code but is reference-exact. **Decide in Phase
3**, and per the plan's "Read Paper Before Patching" discipline, read PRIMME's
`blaslapack.c` usage of both routines before choosing.

| Plan location | Change |

| new | vendored `Makevars` must carry `-pipe` and `-DPRIMME_WITHOUT_FLOAT` |

## 5. Not done

- **Linux build.** No Linux machine was used. Expected to be the easiest of the three, and
  expected *not* to hit the LAPACK blocker when linked against a distro LAPACK, but that is
  an expectation, not a measurement.
- **No bindings**, as the plan specifies for this spike.
- The shim was not validated on complex problems.
