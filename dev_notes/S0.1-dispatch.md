# S0.1 -- `%*%` dispatch, object system, and the R version floor

Run 2026-07-27 on R 4.6.0 (2026-04-24 ucrt), x86_64-w64-mingw32, Matrix 1.7.5, S7 0.2.2.
Scripts: `dev_notes/spikes/S0.1_*.R`. Every claim below was executed; nothing is inferred
from documentation alone except where marked **unverified**.

## Decisions

1. **S3, using the `matrixOps` group generic.** Not S4, not S7.
2. **Depends floor: R (>= 4.4.0).** Not 4.3.0, which the plan assumed.
3. `nrow`/`ncol` need no methods.
4. `crossprod()` follows base R, which means `A^T A`. Plan section 5.4 and the 5.6 table
   have this backwards and are corrected below.
5. The `sparse` leaf is real-only.

---

## 1. The version floor is 4.4.0, not 4.3.0

Plan section 9 S0.1 says "believed 4.3.0, `matrixOps` group generic for S4". Half right.
From R's own NEWS, `C:/Program Files/R/R-4.6.0/doc/NEWS`:

- line 2956, under `Changes in R 4.3.0:` (section header line 2725):
  > "The matrix multiply operator `%*%` is now an S3 generic, belonging to new group
  > generic `matrixOps`. From Tomasz Kalinowski's contribution in PR#18483."

- line 1965, under `Changes in R 4.4.0:` (section header line 1801):
  > "The matrix multiplication functions `crossprod()` and `tcrossprod()` are now also
  > primitive and S3 generic, as `%*%` had become in R 4.3.0."

`crossprod` and `tcrossprod` are in the public generic budget (section 1.1), so the floor
is the version where *they* dispatch: **R >= 4.4.0**. On 4.3.x, `A %*% B` would dispatch
and `crossprod(A)` would silently compute on the underlying list. Silent wrong answers, so
the floor is a hard `Depends`, not a suggestion.

**Unverified:** dispatch was not executed on 4.3.x or 4.4.x; only 4.6.0 is installed. The
floor rests on the NEWS entries above, which are authoritative for when the capability
landed. If it matters more, install R 4.4.0 and re-run `S0.1_matrix.R`.

## 2. One `matrixOps` method covers all three multiply generics

Verified against a namespace-installed package (`dispS3`), not global-env assignment,
because registered methods are what ships.

Class `opG` defines exactly one method, `matrixOps.opG`:

```
G %*% M            -> opG-matrixOps-%*%
M %*% G            -> opG-matrixOps-%*%
crossprod(G)       -> opG-matrixOps-crossprod
crossprod(G, M)    -> opG-matrixOps-crossprod
tcrossprod(G)      -> opG-matrixOps-tcrossprod
```

`.Generic` distinguishes them inside the method. Dispatch fires on the second argument
(`M %*% G`) as well as the first. Likewise one `Complex.opG` covers `Conj`.

This is the O(1) dispatch shape: three generics, one method, one place to change.

Individual methods (`%*%.opA`, `crossprod.opA`, ...) also work; the group method is chosen
because it cannot drift out of sync across the three.

### A wrinkle worth recording

```
methods::getGroupMembers("matrixOps")   ->  %*%
"crossprod" %in% .S3PrimitiveGenerics   ->  FALSE
```

Even on R 4.6.0 the *methods-package* view of the `matrixOps` group lists only `%*%`, and
`crossprod` is absent from `.S3PrimitiveGenerics`. S3 group dispatch for `crossprod`
nonetheless works (proven above) because it is handled in the C evaluator. So
`getGroupMembers()` is not a reliable oracle for what S3 group dispatch covers. Do not
write a test that asserts group membership through `methods::`; assert behaviour.

## 3. S7 0.2.2 cannot carry this package

S7 was the preferred option and it fails on the package's most important generic family.
A minimal S7 package does not install:

```
Error : `generic` is a function, but not an S3 generic function: .Primitive("crossprod")
Error: unable to load R code in package 'dispS7'
```

Per-generic results, after correcting my own signature mistakes (`solve` is single
dispatch; `Ops` members need `e1`/`e2` argument names):

| Generic | S7 0.2.2 | plain S3 |
|---|---|---|
| `%*%` | works | works |
| `crossprod` | **rejected** | works |
| `tcrossprod` | **rejected** | works |
| `t`, `Conj`, `dim`, `as.matrix`, `print`, `summary` | works | works |
| `solve` (single dispatch) | works | works |
| `+`, `*` (with `e1`, `e2`) | works | works |

### Root cause

`S7:::group_generics()` hardcodes the group membership:

```r
if (getRversion() >= "4.3") {
    out$matrixOps <- c("%*%")
}
```

and `S7:::base_matrix_ops` is consequently a one-element list. `S7:::matrixOps.S7_object`
is `base_matrix_ops[[.Generic]](x, y)`, which cannot serve `.Generic == "crossprod"`.
S7 0.2.2 encodes R 4.3.0's group membership and has not been updated for the R 4.4.0
change in section 1. Note this mirrors what `methods::getGroupMembers()` still reports, so
S7 is consistent with the methods package and both lag the C-level behaviour.

### Workarounds exist and are all worse

- Raw `registerS3method("crossprod", <s7 class name>, ...)`, bypassing S7's registrar,
  **does work** (verified). The package would then be S7 for most of its surface and
  hand-rolled S3 for its headline generics. Two systems, one class.
- Registering on the `matrixOps` generic through S7 demands `S4_register()`, which pulls
  S4 back in.

Building the "behaves like a matrix" promise on a workaround around released upstream code
is the wrong foundation for a package whose entire proposition is that the contract is
trustworthy. **S3.**

### Upstream

This is a genuine limitation in a third-party package (r-lib/S7), reproducible in ~10
lines. Worth filing; linop does not depend on the outcome. See
`dev_notes/spikes/S0.1_s7_granular.R` for the minimal repro.

## 4. S4 (control)

S4 works for every generic tested, including separate `signature("ANY", "op4cls")` for
right-hand dispatch. It is not chosen: it needs a method per argument-position for `%*%`,
carries `methods` ceremony throughout, and was ruled out by preference. Recorded here so
the rejection is documented rather than assumed.

## 5. `nrow`/`ncol` are not generic and need no methods

```
nrow  is.primitive: FALSE   body: dim(x)[1L]
ncol  is.primitive: FALSE   body: dim(x)[2L]
```

Both derive from `dim()`. With `dim.linop` defined, `nrow(A)` and `ncol(A)` returned the
right answers for all three object systems with no method written. The section 1.1 budget
lists them under "generics"; they cost nothing and require nothing.

## 6. Correction to plan sections 5.4 and 5.6: base R `crossprod` is `A^T A`

This is the most consequential finding and it inverts a stated design fact.

Plan section 5.4 says:

> "for complex `A`, `crossprod(A) = A^H A` is hermitian, while `t(A) %*% A = A^T A` is
> symmetric and generally not hermitian"

Base R disagrees. With `Z` a 2x2 complex matrix:

```
crossprod(Z) == t(Z) %*% Z        (A^T A) : TRUE
crossprod(Z) == Conj(t(Z)) %*% Z  (A^H A) : FALSE

crossprod(Z)   hermitian: FALSE   symmetric: TRUE
A^T A          hermitian: FALSE   symmetric: TRUE
A^H A          hermitian: TRUE    symmetric: FALSE
```

and identically for `tcrossprod(Z) == Z %*% t(Z)`, not `Z %*% Conj(t(Z))`.

So in base R, `crossprod(A)` **is** the operation the plan calls `t(A) %*% A`. The two
rows of the 5.6 table are the same operation with swapped flags.

### Resolution: follow base R

`crossprod()` on a `linop` must equal `crossprod()` on the materialised matrix, or the
package's central promise is false and the Gate 1 fuzzer (which compares against base R
recomputation from materialised leaves) fails immediately. Corrected rows:

| Expression | hermitian | symmetric | positive definite |
|---|---|---|---|
| `crossprod(A)` = `A^T A` | iff `A` real | always | `NA` (iff full column rank when `A` real) |
| `t(A) %*% A` | identical to `crossprod(A)` above | | |
| `adjoint(A) %*% A` = `A^H A` | always | iff `A` real | iff full column rank, else PSD |
| `tcrossprod(A)` = `A A^T` | iff `A` real | always | `NA` (iff full row rank when `A` real) |
| `A %*% adjoint(A)` = `A A^H` | always | iff `A` real | iff full row rank, else PSD |

For real `A` every distinction collapses and the plan's original table is right, which is
why the error survived drafting.

### Consequence for the algebra

The Hermitian Gram matrix is `adjoint(A) %*% A`. The product node must **recognise**
`adjoint(X) %*% X` (and `X %*% adjoint(X)`) structurally and stamp
`hermitian = TRUE, source = "construction"` with no dependency on `A`'s own flags, since
it holds unconditionally. Section 5.6's `A %*% B -> NA unless B provably A^H` already
anticipates this; the recognition rule is where it becomes real.

The trap the plan wanted to document is still real and still worth documenting, just
stated correctly: **for complex operators `crossprod(A)` is not the Hermitian Gram
matrix.** A user reaching for `crossprod` to build a PSD operator gets a symmetric
non-Hermitian one. That belongs in a vignette.

## 7. The `sparse` leaf is real-only

Matrix 1.7.5 declares the `zMatrix` virtual classes but not the concrete ones:

```
Matrix(Z)                                   -> ERR: invalid 'data'
as(Z, "dgCMatrix")                          -> ERR: "zgeMatrix" is not a defined class
sparseMatrix(i=, j=, x = c(1+1i, 2-1i))     -> ERR: "zgTMatrix" is not a defined class
isVirtualClass("zgCMatrix")                 -> TRUE
```

Real sparse is fine, and `crossprod()` of a `dgCMatrix` returns a `dsCMatrix` that
`is(., "symmetricMatrix")`, which the adapter can read as evidence.

**Gate 1 amendment.** "Conformance suite passes on every node type, real and complex"
cannot hold literally: complex sparse cannot be constructed. Restate as *every node type,
real; and complex on every node whose backing storage admits it (all but `sparse`)*. A
complex operator with sparse structure goes through a `fun` leaf.

Adapter targets confirmed present: `dgCMatrix`, `dsCMatrix`, `dtCMatrix`, `dgeMatrix`,
`dsyMatrix`, `ddiMatrix`, `dgRMatrix`, `dgTMatrix`.
