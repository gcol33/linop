# S0.2 -- R callback overhead for a `fun` leaf

Run 2026-07-27, R 4.6.0, x86_64-w64-mingw32, i9-14900K, reference LAPACK 3.12.1.
Script `dev_notes/spikes/S0.2_callback.R`, results `dev_notes/spikes/S0.2_results.csv`.

## Decisions

1. **Core stays zero compiled code.** The round trip is not expensive. Plan risk 13.2 is
   closed and the contingency C fast path for `fun` leaves is not needed.
2. **Normalise vectors with `dim<-`, never `as.matrix()`.** Measured 7.7x difference.
3. **Block width stays in the design, but the plan's stated reason for it is wrong.**
   Blocks are not needed to amortise call overhead. Corrected rationale below.

## Method note

`proc.time()` was tried first and is unusable: ~1 ms resolution on Windows against
operations of a few hundred nanoseconds, which produced a table of zeros and `Inf`. The
committed script uses microbenchmark's high-resolution counter. Recording this because the
first table looked plausible enough to believe.

## 1. The round trip costs 200 ns

| Operation | ns |
|---|---|
| 1 closure call (identity) | 100 |
| 2 nested calls (leaf wrapper -> user function) | 200 |
| 3 nested calls | 300 |
| `dim()` check on something already a matrix | 100 |
| `as.matrix()` on a length-4 vector | **2300** |
| `dim<-()` on a length-4 vector | **300** |

A `fun` leaf costs two frames, so **200 ns per apply** is the realistic figure.

### `as.matrix()` is the expensive part, and it is avoidable

Section 5.2 mandates that `X` is always a matrix and a vector is `b = 1`. The obvious
implementation, `if (is.null(dim(X))) X <- as.matrix(X)`, costs 2300 ns -- eleven times the
entire call round trip, and by far the largest avoidable constant in the apply path.
`dim(X) <- c(length(X), 1L)` does the same job for 300 ns.

Directive for Phase 1: the vector normalisation helper uses `dim<-`. Never `as.matrix()`
on the hot path.

## 2. Against a real operator the round trip disappears

`call_pct` is the 200 ns round trip as a percentage of one wrapped apply.

| operator | n | b=1 | b=64 |
|---|---|---|---|
| diag `d * X` | 1e3 | **22.2%** | 0.20% |
| diag | 1e5 | 0.126% | 0.0013% |
| diag | 1e7 | 0.00086% | -- |
| tridiagonal | 1e3 | 1.11% | 0.032% |
| tridiagonal | 1e5 | 0.0078% | 0.00023% |
| tridiagonal | 1e7 | 0.000075% | -- |
| dense `M %*% X` | 1e3 | 0.033% | 0.0011% |

The worst case in the entire grid is 22.2%, and that is a diagonal scale of 1000 elements
-- an apply of 0.9 microseconds, the cheapest operator anyone would ever wrap. One step up
in either size or complexity and it is already at 1%. Everything at n >= 1e5 is under
0.13%.

## 3. Krylov-scale extrapolation

The plan's concern: "Krylov runs 1e2 to 1e5 iterations, so if the round trip is expensive
relative to the matvec, block widths become mandatory and some solver designs change."

| applies | pure call overhead |
|---|---|
| 1e2 | 0.00002 s |
| 1e3 | 0.0002 s |
| 1e4 | 0.002 s |
| 1e5 | **0.020 s** |

Twenty milliseconds across a hundred thousand iterations. The premise does not hold, so
nothing downstream of it changes. Core keeps `Imports: methods`-or-less and no `src/`.

## 4. Block width helps, for a different reason than the plan gives

This is the part that does not match the plan's expectation. Per-column cost, b=1 vs the
widest block measured:

| operator | n | per-column speedup at wide b |
|---|---|---|
| dense `M %*% X` | 1e3 | **2.20x** (b=64) |
| tridiagonal | 1e3 | 1.81x (b=64) |
| tridiagonal | 1e5 | 1.91x (b=64) |
| tridiagonal | 1e7 | 1.98x (b=16) |
| diag | 1e3 | **0.58x** (b=64, i.e. *worse*) |
| diag | 1e5 | **0.65x** (b=64, i.e. *worse*) |
| diag | 1e7 | 1.20x (b=16) |

Three regimes:

- **Dense leaves gain 2.2x** because `M %*% X` with wide `X` is BLAS-3 `dgemm` instead of
  repeated BLAS-2 `dgemv`. This is the real and expected win.
- **Interpreted-loop operators gain ~1.9x** because the R-level index arithmetic in the
  tridiagonal apply is paid once per block instead of once per column.
- **Memory-bound O(n b) operators lose.** A pure diagonal scale is *slower per column* at
  b=64 for n = 1e3 and 1e5. `d * X` recycles `d` down a tall matrix; at b=1 the working
  set fits in cache, at b=64 it does not. The arithmetic is identical, the traffic is not.

So blocks are not a universal win, and specifically they are **not** a way to amortise the
callback -- there is nothing to amortise. Section 5.2 justifies block-first on two grounds,
"every block Krylov method needs it" and "retrofitting blocks is a breaking change". Both
survive. The third implied justification, that blocks rescue callback cost, should be
struck; it is unsupported and the diagonal row actively contradicts it.

Consequence for the cost model: `collapse()` and any future planner must not assume wider
blocks are cheaper per column. For memory-bound leaves the optimum block width is small.
The `cost` slot in section 5.1 is flops per column, which cannot express this; it should be
read as an ordering heuristic and never as a predictor of wall time.

## 5. What this fixes in the plan

| Plan location | Says | Should say |
|---|---|---|
| 13, risk 2 | R callback overhead is a live risk with a C fast path contingency | Closed. 200 ns/apply, <=0.13% for n >= 1e5 |
| 17, question 3 | "Does core stay at zero compiled code if S0.2 says callbacks are slow?" | Answered: callbacks are not slow, core stays pure R |
| 5.2 | block-first partly because callbacks are costly | block-first for BLAS-3 on dense leaves and retrofit cost; blocks can be *slower* per column for memory-bound leaves |
| 5.2 | "`X` is always a matrix; a vector is `b = 1`" | implement with `dim<-`, not `as.matrix()`, an 11x-round-trip difference |

## 6. Unverified

Single machine, single BLAS. R ships reference BLAS on Windows by default and `La_library()`
returned empty here, so the dense 2.20x block gain is a *reference*-BLAS number; a threaded
OpenBLAS or MKL would likely widen it. That direction only strengthens the block-first
decision, so it was not chased. Not measured on the Mac mini (Accelerate) or Linux.
